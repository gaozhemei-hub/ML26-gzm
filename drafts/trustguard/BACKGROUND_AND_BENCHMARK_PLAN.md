# TrustGuard 背景资料与基准实验计划

## 1. 问题背景：从可解释到可信

MLJAR `mljar-supervised` 的设计哲学是让用户看到 AutoML 的训练细节：它生成模型报告、
特征重要性、SHAP、学习曲线和自动文档，也支持公平性训练与报告。它是本项目研究
AutoML 报告生成机制的合适基线。

但“解释输出”回答的是模型使用了什么特征、在给定评估数据上表现如何；它不必然回答
这些特征在预测时是否合法、数据划分是否独立、测试分数是否被用于反复选模型。Kapoor
等关于数据泄露与可复现性危机的研究正指出：违反这些原则时，模型性能可能被虚高。

TrustGuard 的研究问题是：

> 现有 AutoML 的报告是否同时生成足够的工件，让使用者判断实验结论是否可信？

## 2. 竞品对照范围

MLJAR 的公开报告体系覆盖模型训练、解释与公平性。TrustGuard 在此基础上将数据泄露、
测试集访问、实验取证以及数据漂移/群体覆盖作为默认、可审计的风险工件。

| 工件类别 | MLJAR 基线 | 原 TabularX | TrustGuard 扩展 |
|---|---|---|---|
| 模型指标、排行榜、报告 | 记录 | 记录 | 复用原有输出 |
| SHAP/重要性/学习曲线 | 记录 | 记录 | 复用原有输出 |
| 公平性 | 支持 | 支持 | 增加群体样本覆盖检查 |
| 目标/ID/代理字段泄露 | README 未列为专用强制审计工件 | 未发现独立审计 | 强制生成风险工件 |
| 实体/重复/时间泄露 | README 未列为专用强制审计工件 | 未发现独立审计 | 强制生成风险工件 |
| 测试集访问日志 | README 未列为专用强制审计工件 | 当前每个候选读取测试集 | 强制单次访问 |
| 数据/划分/环境/工件证据链 | README 未列为完整证据链工件 | 有部分种子与指纹 | 完整本地证据包 |
| 特征漂移/群体覆盖 | README 未列为专用强制审计工件 | 仅分类标签比例 | PSI/KS/TVD/覆盖表 |

## 3. 数据集与实验矩阵

选择 5 个 CC-18 task，而不是手工挑选有利数据集。使用
`create_cc18_manifest(..., limit=5)` 固化 task ID；如时间充足改为 `limit=10`。

每个数据集运行：

| 实验 | 工具 | 目的 |
|---|---|---|
| E1 | MLJAR Explain | 记录既有可解释性工件 |
| E2 | 原 TabularX | 记录原项目工件及评估协议风险 |
| E3 | TabularX + TrustGuard | 记录四类可信性工件 |
| E4 | E3 + 注入泄露 | 验证风险能被发现/阻断 |

注入实验只用于研究验证，不用于真实业务数据：

- `target_copy`：复制目标列，预期为 critical；
- `id_like`：创建高唯一性标识符，预期为 medium/high；
- `cross_split_duplicate`：复制部分样本到其他划分，预期为 critical；
- 可选 `future_signal`：对真实时间数据使用未来信息字段，需人工声明时间列。

## 4. 记录哪些结果

每次运行保存：

- 数据集 task ID、目标列、样本数、特征数、固定配置与时间预算；
- 各工具产生的工件清单；
- TrustGuard 各模块的风险等级、发现数与处理建议；
- 正常/注入泄露时的主要指标变化；
- 运行失败也记录原因，不静默删除。

实验结果汇总表如下：

| task_x | 原 TabularX | ✓ | ✓/配置后 | – | 风险 | 部分 | 标签比例 | ... |

## 5. 有效性边界

该实验关注“报告与风险工件的完整性”，不是在不同 AutoML 工具间宣称绝对公平的性能排名。
因为各工具默认验证策略、模型预算和集成策略可能不同。若要比较性能，必须额外统一：
任务划分、总训练预算、随机种子、模型候选和硬件资源。
