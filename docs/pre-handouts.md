## 第一部分：问题引入（1.5 分钟）

大家好，我选的题目是 TabularX——一个面向可解释性与可复现性的自动化表格建模工具包。

（翻页）

现在做表格数据的 AutoML，工具已经很多了。MLJAR、AutoGluon、H2O，都能自动帮你选模型、调参数、做预处理。你只需要把数据丢进去，等它跑完，拿一个模型出来。这件事本身已经很成熟了。

但问题是——跑完之后，你拿到的是一个模型。至于数据是怎么预处理的、模型为什么选这个不选那个、每个特征对预测有多大贡献、模型在哪些群体上可能表现不公平——这些信息要么没有，要么散落在代码里，需要你自己去翻。

（翻页）

所以我们的问题很简单：**能不能让 AutoML 的每一次运行，都强制产出一份完整的、可读的实验记录？**

——不是「可选」的导出功能，而是每次 `fit()` 结束之后，一个完整文件夹自动摆在那里，里面是数据概况、划分方案、预处理流水线、模型排名、SHAP 解释图、公平性审计报告，全都有。

这就是 TabularX 要解决的问题。

## 第二部分：Baseline——MLJAR 的设计哲学（3 分钟）

在实现之前，我们首先研究了 MLJAR 这个标杆。mljar-supervised 是目前表格 AutoML 中最成熟的开源项目之一，它在设计上有几个值得我们学习的原则。

（翻页）

**第一条：注册表 + 能力声明。**

MLJAR 里每个模型族在注册时，会声明自己「需要哪些预处理」。比如线性模型和神经网络要求标准化，随机森林和 XGBoost 不需要，CatBoost 连类别编码都不需要——因为它自己能处理。框架根据模型的能力声明，自动匹配合适的预处理策略，不做一刀切。

（翻页）

**第二条：Profile 只报事实，不做决策。**

MLJAR 把数据观测和预处理决策分成两层。第一步，`DataInfo` 模块只去「看」数据——哪些列是数值、哪些是类别、哪些有缺失、哪些偏态严重。第二步，`PreprocessingTuner` 再根据「数据事实」和「模型能力」的交集做出决策。Profile 只管描述，不管怎么处理。

（翻页）

**第三条：先划分，再预处理。**

这是一个容易犯错但极其重要的原则。划分是实验设计，预处理是数据变换。变换的统计量只能从训练集计算，否则会造成数据泄露。MLJAR 始终坚持先划分、后预处理，这是正确的做法。

（翻页）

**第四条：产物自包含 + 元数据驱动。**

MLJAR 每个实验目录就是一个完整快照——顶层有 `data_info.json` 描述列信息、`params.json` 记录运行参数、`leaderboard.csv` 列出所有模型的分数；每个模型目录里还有 `framework.json` 记录预处理策略、验证策略、模型参数和训练时间。打开一个目录，就知道这次实验做了什么。

（翻页）

**这四条设计原则给了我们很好的起点。在实现 TabularX 时，我们继承并进一步推进了这些理念。**

## 第三部分：TabularX 的设计（3.5 分钟）

### 架构层面（2 分钟）

TabularX 在架构上做了几件事。

（翻页）

**第一，纯函数分层。**

这是 TabularX 最核心的架构决策。我们把整个流水线拆成独立的阶段——Profile、Split、Preprocess、ModelSearch、SHAP、Fairness——每个阶段都是纯函数，只做计算，不做 IO。Profile 只返回 `DataProfile` 对象，不写文件；Split 只返回 `SplitResult`；Preprocess 只返回 `PreprocessedData`。IO——写 HTML、存模型、保存图片——全部交给最外层的 `estimator` 管。

这样做的好处是，每个阶段的测试只需要「给输入、断言输出」，不需要 mock 文件系统。

（翻页）

**第二，Schema 契约解耦阶段间依赖。**

阶段之间不直接依赖对方的实现，只通过 dataclass 通信。Profile 的输出是 `DataProfile`，Split 的输入和输出是 `SplitResult`，Preprocess 产出 `PreprocessedData`。只要契约不变，内部实现可以随便换。这和各阶段的参数配置一样，所有的配置集中在一个 `TabularXParams` 类里，不需要到每个模块去翻。

（翻页）

**第三，继承 MLJAR 的两层架构。**

注册表 + 能力声明的机制从 MLJAR 继承下来，按 binary / multiclass / regression 三个桶管理模型。Profile 只做观测、不做决策的原则也同样沿用。

### 功能层面（1.5 分钟）

架构之上，TabularX 在功能上有三个亮点。

（翻页）

**第一个：强制报告生成。**

这是 TabularX 最核心的差异化点。报告不是用户主动导出才有的——不是。每次 `fit()` 运行完毕，下面这些产物自动生成：

- 数据概况报告
- 数据划分报告
- 预处理流水线报告
- 每个模型的独立报告（含评估指标、混淆矩阵、ROC、调参轨迹）
- 模型搜索排名报告
- SHAP 解释报告（特征重要性排序 + 汇总图 + Waterfall 图）
- 公平性评估报告
- 最佳模型文件
- 完整合并报告（HTML + 可选 PDF）

一套流程跑下来，一个完整的实验目录自动成型。

（翻页）

**第二个：原生公平性审计。**

用户只需要在 `fit()` 时多传一个参数——`sensitive_features`，指定敏感特征。框架会自动把测试集按敏感特征分组，计算每组的 Demographic Parity 和 Equalized Odds 差异，超阈值自动告警。不需要额外写代码，不需要调什么复杂配置。

（翻页）

**第三个：每个模型都有完整的独立报告。**

MLJAR 主要对最优模型做详细解释。TabularX 的做法是：搜索环节所有成功跑完的模型，都有自己的独立报告页面——包含评估指标、混淆矩阵（分类任务）、ROC 曲线（二分类）、调参轨迹图。对比优势一目了然。

## 第四部分：最终使用和输出效果示例（2 分钟）

理论讲完了，直接看效果。

我们拿 Breast Cancer 数据集——二分类，569 个样本，30 个特征，做一次完整的 TabularX 流水线。

（翻页）

先看模型排名。这是运行结束后 `result.searched.ranking` 的输出。四个模型都跑了，XGBoost 以 0.9934 的验证 AUC 排第一，测试集 0.9911。LightGBM 验证集最高但测试集略低。排名表格、验证分数、测试分数，一目了然。

（翻页）

再看 SHAP 可解释性。对最优模型做 SHAP 分析，Top-10 特征的解释力占比。排第一的是 worst concave points，平均 |SHAP| 值 0.90，远高于其他特征。这意味着这个特征是预测恶性和良性的最关键信号。我们还生成了 SHAP summary 图和 waterfall 图，特征贡献方向也看得很清楚。

（翻页）

然后是公平性评估。我们把 mean radius 分成 small / medium / large 三组，模拟敏感特征传入 `fit()`。输出显示，Demographic Parity 差异 0.94，Equalized Odds TPR 差异达到 1.0——框架自动标红告警。原因是 large 组只有 4 个样本且全是良性，导致估算不稳定。但这个例子展示的是：工具确实能自动报告，你不必自己去算。

（翻页）

最后看报告目录。一次 `fit()` 跑完，输出目录结构是这样的：

```
intro1-output/
├── best_model.joblib
├── report.html                      # 完整合并报告
└── reports/
    ├── profile.html                 # 数据概况
    ├── split.html                   # 划分方案
    ├── preprocess.html              # 预处理流水线
    ├── model_search.html            # 模型搜索排名
    ├── explanation.html             # SHAP + 公平性
    ├── assets/                      # 图片
    └── models/                      # 每个模型的独立报告
        ├── xgboost.html
        ├── random_forest.html
        └── ...
```

每个 HTML 直接用浏览器打开就能看，不需要任何额外工具。

（翻页，结束）

**总结一句**：TabularX 不是要做一个「精度更高」的 AutoML。AutoML 在精度上已经很成熟了。TabularX 要做的是——让 AutoML 的每一次运行都留下完整的、可追溯的、包含公平性审计的实验记录。数据怎么处理的、模型为什么选这个、对哪些群体可能有偏见——所有这些问题，打开报告文件夹，就有答案。
