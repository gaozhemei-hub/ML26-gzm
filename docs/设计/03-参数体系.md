# 参数体系

## 设计哲学：参数集中、校验前置

- **集中**：所有可调参数定义在 `core/params.py` 中，不分散在各阶段模块里
- **前置**：参数校验在 Config 构造时完成（`__post_init__`），下游函数假设"拿到的参数已经是合法的"

这样做的结果是：用户通过 `TabularXParams` 一眼就能看到所有可调参数，而不需要翻遍每个阶段的实现。

## 三层嵌套

```
TabularXParams
├── ProfileConfig      （10 个参数：类型判定阈值、scale 判据、数据量下限……）
├── SplitConfig        （4 个参数：test_size、validation_size、random_state、min_samples_split）
└── PreprocessConfig   （1 个参数：skew_method，当前仅占位）
```

每个子 Config 独立定义自己的一组参数，互不干扰。需要新增一个阶段的参数时，新增一个 `XxxConfig` 并在 `TabularXParams` 中注册即可。

## 校验策略

### 两层入口，两种约束力度

| 入口 | 是否校验 | 适用场景 |
|---|---|---|
| `tx.params.profile.threshold = -1`（直接 `=` 赋值） | ❌ 不校验 | 快速原型、高级用户确知自己在做什么 |
| `tx.params.set_param("profile", "threshold", -1)` | ✅ 校验 | 生产代码、需要保护 |

保留 `=` 赋值不校验是有意为之：Python dataclass 允许直接写字段是语言特性，强行拦截会破坏直觉。用户选择走快捷路径，也就接受了相应的风险。

### 校验什么

- **单字段定义域**：通过 `_RANGES` 字典定义每个字段的取值范围（全闭区间 `[lo, hi]`）
- **跨字段推导不变量**：如 `SplitConfig` 会在构造时推导 `train_ratio = 1 - test_size - validation_size × (1 - test_size) > 0`，如果组合导致训练集占比为零则报错。这类检查放在 Config 层意味着**这种不变量在参数生效前就已经被强制满足**，下游不需要再检查

### 校验不做什么

不检查参数的"业务合理性"（比如 `text_unique_threshold` 超过样本数）。这类检查依赖数据，属于 flow 函数的职责，不放在参数层。

## 统一接口

每个子 Config 暴露同一组方法：

| 方法 | 作用 |
|---|---|
| `set_param(name, value)` | 带校验修改 |
| `get_comments(name)` | 返回中文注释 |
| `overview()` | 总览所有参数及当前值 |
| `to_dict()` | 序列化 |

`TabularXParams` 提供类似的代理方法，加上 `reset()` 恢复默认值。这套接口的设计目标是一个用户只需要学一次 API，就能操作所有参数。

## 为什么参数要设计成 dataclass 嵌套而非纯字典/JSON

- **类型提示**：`tx.params.split.test_size` 在 IDE 中有自动补全和类型推断
- **默认值集中**：修改默认参数只需要改一处字段默认值，不需要翻配置文件和代码之间的映射
- **校验内聚**：校验逻辑和参数定义在同一个类中，不需要额外的校验器模块
