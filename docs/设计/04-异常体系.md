# 异常体系

## 分层结构

```
TabularXError（所有异常的基类，可选携带 stage 属性）
└── DataError（数据有问题，用户可修复）
    ├── Profile 阶段异常
    │   ├── InvalidDataError      — X 不是 DataFrame / y 不是 Series
    │   ├── EmptyDataError        — X 或 y 为空
    │   ├── MismatchedLengthError — X 与 y 行数不一致
    │   ├── EmptyTargetError      — y 去空后为空
    │   ├── TaskTypeError         — 无法推断任务类型
    │   └── InsufficientDataError — 样本数不足
    └── Split 阶段异常
        ├── InvalidSplitError     — 子集样本数不足 min_samples_split
        └── StratifyError         — 分层采样失败（类别样本不足）
```

## 设计原则

### 只针对"数据问题"定义自定义异常

参数越界、参数名错误等"调用方传参错误"直接抛 Python 内置的 `ValueError`，不包装成自定义异常。原因是：

- **调用方不需要为传参错误写 catch**——这是 bug，不是运行时异常。bug 应该让程序崩溃，而不是被吞掉
- **链式一致性**：标准库函数（如 `train_test_split`）也是在参数非法时抛 `ValueError`，我们的自定义异常如果也抛 `ValueError`，调用方无法区分是 sklearn 的错还是我们的错

### 所有自定义异常继承 DataError

意味着调用方只需要写 `except TabularXError:` 就能捕获所有业务异常，或者写 `except DataError:` 来捕获"我可以修"的异常。没有定义 `ConfigError`、`IOError` 等兄弟分支——那些要么不存在（参数字典用 `ValueError`），要么由上层负责（IO 由调用方管理）。

### 异常消息中包含修复建议

每个异常消息的末尾都附带"建议"或"可通过……解决"的提示。这是报告驱动设计的体现：用户在终端看到错误时，不需要翻文档就知道怎么修。

## 异常 vs 校验的边界

| 问题类型 | 检测位置 | 异常类型 | 示例 |
|---|---|---|---|
| 参数越界 | `Config.__post_init__` | `ValueError`（内置） | test_size = -0.1 |
| 参数名不存在 | `Config.set_param()` | `ValueError`（内置） | set_param("no_such_param", 1) |
| 数据格式不对 | flow 函数开头 | `DataError` 子类 | X 不是 DataFrame |
| 数据量不足 | flow 函数中 | `DataError` 子类 | 样本数 < min_samples |
| sklearn 调用失败 | flow 函数中 | `DataError` 子类 | stratify 失败 |

这条边界不是随意定的，它的依据是**调用方能做什么**：
- 参数越界：调用方改参数值 → 这是编码阶段的错误，不需要 catch
- 数据有问题：调用方换数据或调参数 → 这是运行时的可恢复异常，需要 catch
