# 报告渲染机制

## 纯函数设计

`reports.py` 是纯渲染层，输入是 schema 对象 + 报告类型，输出是 HTML 字符串。不做 IO：

```python
html_str = render_profile_report(data_profile)
# 写文件是调用方的事
with open("report.html", "w") as f:
    f.write(html_str)
```

这样设计的理由：

- **可测试**：测试断言就是 `assert "期望文本" in render_report(...)`，不需要建临时目录
- **可组合**：HTML 字符串可以嵌入网页、作为邮件正文、或批量生成后打包下载
- **可替换**：以后如果要支持 PDF 或 Markdown，只需要新增渲染函数，不需要改调用方逻辑

## 架构

```
render_profile_report(DataProfile)  →  render_report(ReportType.PROFILE, data)
render_split_report(SplitResult)    →  render_report(ReportType.SPLIT, data)
                                                      │
                                                      ▼
                                              render_template(template_name, data)
                                                      │
                                                      ▼
                                            Jinja2 Environment + 模板文件
```

`ReportType` 枚举的取值就是模板文件名，不需要维护额外的映射表：

```python
class ReportType(Enum):
    PROFILE = "profile_report.html.jinja2"
    SPLIT = "split_report.html.jinja2"
```

新增一种报告时：注册枚举 + 写模板 + 加便捷函数，三步完成。

## 模板的策略

- **三层结构**：摘要 → 判断流程与证据（含 Mermaid 流程图） → 详细数据
- **Mermaid 流程图**：不是装饰，是报告的核心卖点。它让每个阶段的判断逻辑可视化，首次使用的用户也能理解"系统为什么这样处理我的数据"
- **Evidence 展示约定**：每条证据以 `metric = value — note` 的格式呈现，用户在流程图和证据列表之间来回对照，建立从"流程"到"具体数据"的映射

## 报告与核心函数的职责边界

- **核心函数**（core/）负责：产生数据、记录证据、做决策
- **渲染层**（reports/ + templates/）负责：格式化展示、绘制流程图、组织信息层级

渲染层不重复核心函数的逻辑。模板中不写 if/else 判断业务规则（"是否要 scale"这类逻辑不在模板中判断），只做展示层面的条件分支（"如果有 evidence 就渲染证据区域"）。
