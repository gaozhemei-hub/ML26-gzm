# 架构总览

## 分层设计

TabularX 的分层围绕一个核心约束：**各阶段的逻辑必须与 IO 解耦**。每一层要么是纯函数（零 IO、零副作用），要么是纯数据契约。IO 由最外层的调用方负责。

```
┌─────────────────────────────────────────────────────────────┐
│                      调用方（用户代码 / CLI）                 │
│  负责：读数据、写报告、写产物、编排流程                       │
│  有 IO                                                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌───────────┐   │
│  │ Profile  │  │  Split   │  │Preprocess│  │    ...    │   │  core/（纯函数）
│  │  观测     │→│  划分     │→│  预处理   │→│ ModelSearch│  │
│  └──────────┘  └──────────┘  └──────────┘  └───────────┘   │
│       │              │             │                         │
│       ▼              ▼             ▼                         │
│  ┌─────────────────────────────────────────┐                │
│  │           参数配置 TabularXParams         │                │  core/params.py
│  │          ProfileConfig / SplitConfig /   │                │  （纯函数）
│  │               PreprocessConfig           │                │
│  └─────────────────────────────────────────┘                │
│       │              │             │                         │
│       ▼              ▼             ▼                         │
│  ┌─────────────────────────────────────────┐                │
│  │             数据契约（schema）            │                │  schema/（纯数据）
│  │   DataProfile → SplitResult → ...       │                │
│  │     各阶段的"输入/输出协议"               │                │
│  └─────────────────────────────────────────┘                │
│                                                             │
│  ┌─────────────────────────────────────────┐                │
│  │              异常体系 TabularXError      │                │  exceptions/
│  │        DataError  → 用户可修复           │                │  （纯定义）
│  └─────────────────────────────────────────┘                │
│                                                             │
│  ┌─────────────────────────────────────────┐                │
│  │          报告渲染层 reports.py           │                │  reports/ + templates/
│  │     DataProfile/SplitResult → HTML      │                │  （纯函数）
│  └─────────────────────────────────────────┘                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 各层职责

### core/ —— 纯计算逻辑

每个模块对应一个阶段，**只做计算，不做 IO**。函数签名遵循统一的模式：

```
result = stage_function(X, y, input_contract, config?)
     ↑        ↑       ↑       ↑               ↑
   返回值    数据    目标   前一阶段的输出    本阶段参数
```

- 不读写文件
- 不打印日志（抛异常是唯一的非正常出口）
- 不依赖全局状态

### schema/ —— 阶段间的通信协议

纯 dataclass，不含业务逻辑。每个阶段输出一个 schema 对象，作为下一个阶段的输入。这层存在的价值是：**让两个阶段之间只靠类型契约耦合，不依赖对方的内部实现**。

### exceptions/ —— 领域异常

自定义异常只在"数据有问题"时抛出。参数越界等底层问题直接用 Python 内置的 `ValueError`，不额外包装——因为调用方不需要 catch 一个 `ConfigError` 来知道参数传错了。

### params.py —— 参数配置

参数集中管理，而不是分散在各自的模块里。这样做的好处：
- 用户在一个地方就能看到所有可调参数
- 参数校验在构造时完成，下游模块可以假设"拿到的参数已经是合法的"
- 实验配置的序列化/反序列化只需要这一个入口

### reports/ + templates/ —— 报告渲染

纯函数：传入 schema 对象，返回 HTML 字符串。不写文件、不读外部资源。调用方拿到字符串后决定写到磁盘、展示在网页还是作为邮件附件。

## 数据流

```
build_profile(X, y)                    → DataProfile
split_data(X, y, DataProfile, config)  → SplitResult
preprocess(X, y, DataProfile, SplitResult, config)  → PreprocessedData
...
```

数据流是单向管道：每个阶段只依赖前一阶段的输出，不跳过、不回溯。这保证了实验的可复现性——给定相同的输入和参数，整条管线产生确定性的输出。

## 为什么这样分

- **纯函数便于测试**：不 mock 文件系统，不 mock 数据库，测试就是"给输入，断言输出"
- **schema 解耦阶段**：profile 不需要知道 split 怎么实现的，只要知道它输出 `SplitResult`
- **参数集中管理**：新增一个可调参数时，只改一个文件（`params.py`），不需要在各模块之间对齐
